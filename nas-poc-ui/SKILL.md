# NaS PoC UI — 用途から配置を選ぶ Liquid Blue

NaSの商談用Web PoCで、信頼感と技術力を伝える。PCとスマホを同じ重みで扱う。
対話で選んだ「リキッド・ブルー」と、改善した入力欄・フォームを共通基準にする。**見た目は統一し、画面構成はその画面で達成する作業から選ぶ。** 方向性と以下の禁止事項はユーザーの決定であり、CSSの数値は再現用の初期値として扱う。

## 用途を読み取り、配置を決めてから実装する

AIが適した構成を選び、理由を短く伝えて実装する。毎回複数案の選択をユーザーに求めない。既存アプリでは画面と主要経路を先に確認し、機能、データ、既存の使い慣れた流れを把握する。見た目だけの変更依頼では、依頼と関係のない情報構造まで組み替えない。

### 1. 判断に必要な情報を得る

会話、仕様、既存コードから分かることは引き継ぎ、同じことを聞き直さない。配置が変わる情報だけを確認する。

- **利用者と達成したいこと**：誰が、何を完了すれば成功か。画面ごとに「対象を探す→内容を判断する→更新する」のように主な流れを捉える。
- **情報の関係**：一覧と詳細か、作業面とその設定か、独立した複数の業務か。何と何を同時に見たり比較したりする必要があるか。
- **操作の頻度と負荷**：繰り返す操作、たまに使う設定、入力の長さ、データ件数、一括処理の有無。
- **利用環境**：PC・スマホの作業内容、マウス・キーボード・タッチ、カメラや横向き表示。未指定なら両端末を同じ重みで設計する。

たとえば「顧客管理」だけで、一括比較と1件ずつの確認のどちらが中心か不明なら、その点を質問する。複数案が妥当でも、目的と既存の流れから判断できれば選んで進める。軽微な未指定事項は合理的な仮定を短く示す。列幅や角丸などの実装上の判断までユーザーに委ねない。

### 2. 主な作業に合う構成を選ぶ

[配置パターンと選定基準](references/layout-patterns.md)の早見表を読み、該当する節を参照する。8パターンは出発点であり、全アプリを分類し尽くすものでも、画面に必ず追加する部品の一覧でもない。

- 入力して一つの結果を得る → 単一作業。
- 会話しながら考える → 会話中心。成果物の編集や根拠の照合も必要なら補助領域を検討する。
- 項目を探し、順に確認・更新する → 一覧・詳細。多数の項目を横断比較するなら表を優先する。
- 候補を探して絞り、比較して選ぶ → 検索・比較。
- 必要事項を記入し、登録・申請を完了する → フォーム・手順。
- 状況を把握し、対応すべき異常や対象を見つける → 監視・分析。
- 対象を見ながら位置や内容を操作する → 作業面・補助パネル。
- 工程や日時を見ながら対象を動かす → 進行・時間軸。

アプリ名だけで決めず、**画面単位**で選ぶ。案件一覧は一覧・詳細、登録はフォーム、営業分析は監視・分析のように組み合わせられる。同時表示の必要性がなければ、複数のパターンを一画面に詰め込まない。カタログ外の作業も、主領域と情報の関係から構成する。

### 3. 各部品の役割と位置を決める

次の判断を実装前に短くまとめる。既存の設計書があれば追記し、単純な変更では会話内の説明でよい。独立した設計文書を毎回増やさない。

- **中心の領域**：何を一番広く、読みやすく、操作しやすく見せるか。
- **主操作と補助操作**：主操作を対象や結果と結び付く位置へ置く。頻繁な操作は直接使えるようにし、低頻度の設定は必要時に開けるようにする。
- **同時表示**：一覧・詳細、根拠・回答、プレビュー・設定などを並べる必要があるか。幅が足りないときは何を残すか。
- **移動と復帰**：全体ナビの要否、詳細からの戻り先、選択・入力・スクロール位置の保持。
- **スマホへの組み替え**：縦積み、詳細への遷移、必要時のパネルのどれが合うか。キーボード表示中の操作も考える。

説明例：「案件を順に確認するため、PCは一覧と詳細を並べます。スマホは詳細へ移動し、戻ると絞り込みと位置を保持します。横断比較が中心になれば、一覧を表に寄せます。」

この説明は選定の根拠と主なトレードオフを伝えるためのもの。採用前に必ず承認を待つ手続きにはしない。画面の中に実装者向けの選定理由を表示しない。

## ナビゲーションと操作を分ける

- **トンマナの適用を理由に、フッター風の選択メニュー・固定下部ナビ・サイドバーを自動で新設しない。** 共通化するのは配色、質感、文字、余白、入力部品などの表現であり、画面構成を一律に固定するものではない。
- **全体ナビ**：独立した業務や画面群を行き来するために使う。少数で短い項目ならヘッダー、大きな階層や項目群ならサイドバーなどを検討する。スマホの下部ナビは、少数の主要な行き先を頻繁に切り替える場合の候補。画面数だけで自動採用しない。
- **その画面の操作**：追加、保存、撮影、生成などは対象の近くや用途に合うツールバーに置く。これらを画面移動のタブに見せない。
- **同じ対象の表示切り替え**：一覧／ボード、期間、絞り込みなどは対象領域に付ける。全体ナビと混同しない。
- **手順**：入力→確認→完了は進捗と戻る／次へで表現する。独立した画面を自由に切り替えるナビとして扱わない。
- 一つの作業が中心なら、近くのボタン、必要時に開くパネル、同じページ内のまとまりを候補にする。ガラス表現を見せるためにナビを増やさない。
- 全体ナビを採用した場合は、現在位置と項目の意味を保つ。レスポンシブ変更で表示形式が変わっても、選択や作業中のデータを失わせない。

## ブランドと不要な装飾

- 淡い青を基調に、落ち着いた文字色と明確な操作で信頼感を作る。強い青は主操作と選択状態に絞る。
- PoCにはNaSのロゴを入れない。ロゴの代わりのマークも自動で作らない。
- **「営」のような文字を丸に入れた、根拠のないユーザーアバターを作らない。** 画面の空きを埋めるために、架空のプロフィール、イニシャル、アカウントメニューを足さない。
- ユーザー・アカウント操作が実際の要件にある場合は、その操作に必要な表示を設計する。装飾目的のアバターとは区別する。
- ナビゲーションや操作を説明する機能アイコンは使える。既存のアイコンセットを統一して使い、主要操作には文字ラベルを付ける。

## ガラスとレイアウト

- Appleのアプリ画面とLiquid Glassの考え方を参考にする。製品紹介ページの大きなヒーローや宣伝用の構成にはしない。
- ガラスは、必要な操作層に使う。既存のツールバーや用途に合う操作パネルなどに適用し、これらの部品を一律に追加しない。本文、チャット回答、一覧、フォーム全体を透かさない。
- 背後の淡い青がわずかに透け、ぼかしと細い光の縁で浮いて見える質感にする。強い発光、大きな影、過剰なガラスの重なりは避ける。
- 本文を大きな角丸カードで何重にも囲わない。余白、文字の階層、必要な区切りで整理する。
- 丸みは残しつつ引き締める。ガラス面14px、ボタン10px、入力欄8pxを初期値にし、すべてをカプセル形にはしない。
- 背景が単調なときは、操作部の背後に控えめな青の色面を置くことはできる。全画面に装飾を増やすためのものではない。
- Webのぼかし・透明度・ハイライトで近づける表現であり、AppleのネイティブLiquid Glassそのものと説明しない。

## 実装への組み込み

配色と素材を実装するときは [assets/tokens.css](assets/tokens.css) を読む。既存のフレームワーク、コンポーネント、テーマの仕組みに合わせて取り込む。新しいUIライブラリを前提にしない。

- スタイルをアプリのルートにスコープし、既存画面の全体スタイルを上書きしない。
- ガラス表現がなくても操作できる、不透明な代替面を用意する。透明度低減の設定と動きの低減設定を尊重する。
- テーマは既存アプリの設定を引き継ぐ。ライト・ダークの両方がある場合は、それぞれで文字と入力欄を読める状態にする。
- 列数やブレークポイントは、各領域に必要な幅と内容から決める。PC画面をそのまま縮小して文字や操作対象を小さくしない。中間幅も確認する。
- 狭い幅では、一覧と詳細を順に見せる、補足を主内容の下へ置く、設定を必要時に開くなど、主作業を保つ形に組み替える。比較が必要な表を無条件にカード化しない。
- モーダルは短く区切れる作業に使う。背後の作業面を見ながら連続調整する場合は、同じページ内や非モーダルの補助領域を検討する。開くたびに主対象を隠す構成にしない。
- モーダルを使う場合は、名前、初期フォーカス、内部のキーボード移動、閉じる操作とフォーカスの復帰を実装する。パネルの移動・閉鎖・リサイズ後も選択と入力を保持する。
- 固定ヘッダー、入力部、下部操作が本文、エラー、フォーカス位置を隠さないようにする。ページと各パネルのスクロール範囲を明確にする。
- フォームの編集文字は16px程度、タップ対象は44px程度を目安にする。必須情報をホバーだけに隠さない。

## 画面ごとの適用

### AIチャット

- 会話中心の画面では会話本文を主役にし、回答を装飾カードで分断しない。成果物を直接編集する作業では、その領域を主役にできる。回答の見出しと段落で情報を整理する。
- 案件などの参照対象をコンパクトに示す。根拠データがある場合は、参照元を開いて確認できるようにする。
- 入力は一行分の高さから始め、文章量に合わせて広げる。大きな空の入力カードを常時置かない。入力面の右に送信ボタンを置き、参照情報などの補足は面の外に小さくまとめる。
- メッセージのラベルを残し、送信は文字で示す。入力文字は16px程度、送信の操作対象は44px以上を初期値にする。空入力では送れず、送信後は入力欄を初期の高さへ戻す。
- 送信・処理中・応答・失敗の状態を、実際に接続している機能に合わせる。サンプル応答を本物のAI生成と誤認させない。

### 顧客・案件管理

- 顧客名、案件名、進行状況、次のアクションを優先する。見せる業務に必要な項目だけを並べる。
- 案件登録など、その画面の主操作を分かりやすく置く。画面を埋めるための集計カードを増やさない。
- スマホで行を縦に組み直す場合は、顧客・案件のまとまりを保つ。横断比較や工程の位置関係が必要なら、選んだ表・ボードの構成を優先する。状態は色だけでなくラベルで示す。

### 入力画面

- ラベルと必須・任意を入力前後とも見える位置に残す。顧客名・案件名・ステータスなどの短い基本項目は、一つの静かな塗りの面にまとめ、項目間を細い線で区切る形を基本にする。項目ごとに大きな枠を繰り返さない。
- 短いラベルは入力の左に置ける。狭い幅や長いラベルでは上下へ組み直し、編集する文字の幅を確保する。長文のメモは別の複数行入力に分ける。
- 入力中は淡い青と控えめな境界色で対象を示す。ガラスは入力欄そのものに重ねず、文字の読みやすい面を使う。既存のキーボードフォーカス表示を消さない。
- 必須項目のエラーは対象の近くに短く表示し、`aria-invalid` と説明の関連付けを使う。修正中も入力内容を保持し、保存後は結果が分かる表示にする。
- 保存を青の主操作、キャンセルを控えめな文字操作として区別し、実際の保存先と挙動に合わせる。

## 選んだ構成を主要経路で確かめる

- 架空のデータを使う場合は、サンプルだと分かる表示にする。表示するボタンはデモの範囲で意味のある反応を持たせる。
- PC幅・スマホ幅・中間幅で、今回のPoCの主要経路を実際に操作する。画面切り替えの回数、主作業を隠す部品、閉じて開き直す反復が多ければ、配置を見直す。
- 一覧→詳細→戻る、パネルを開く→編集→閉じる、幅変更など、採用した構成に応じて状態保持を確かめる。フォームならエラー→修正→保存、チャットなら送信→応答／失敗を確認する。
- 空、読み込み、エラー、件数や文章量が多い状態でも、次に取れる行動が分かるか確認する。商談の正常系だけで配置を決めない。
- 320 CSS px相当の狭い幅や拡大表示で、情報や操作が失われず、不要なページ全体の横スクロールがないか確認する。表・地図・編集キャンバスなど二次元配置が必要な部分は個別に扱い、その周囲のフォームや操作部は組み替える。
- タッチとキーボードで主要操作を使えるか、フォーカスや入力中の対象が固定部品に隠れないか確認する。ドラッグに依存する操作には代わりの操作を用意する。
- 不要なロゴ、文字アバター、プロフィールの飾りを追加していないか確認する。
- 完了時は、採用した構成と理由、確認できた操作、残る制約を短く伝える。検証していない端末や接続を確認済みと説明しない。

## 根拠となる資料

[公式資料と、このスキルでの判断への使い方](references/sources.md)を参照する。Apple HIG、Materialの基本レイアウト、W3Cのフォーム・リフロー・ダイアログの資料を基にしている。プラットフォーム固有の位置、部品、数値をWebへそのまま移植しない。

8つの用途別パターンと選定手順は、公式の原則をNaSのPoC向けに整理した設計上の判断。公式が定めた唯一の分類や、実測で最適性が保証された構成とは説明しない。NaSの配色、ロゴを入れない方針、アバターの扱いはこの対話で決めた独自ルールとして適用する。
