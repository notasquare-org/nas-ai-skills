# 用途から選ぶ画面内の配置

まず早見表で候補を絞り、該当する節だけを読む。以下はNaS向けの設計ガイドであり、固定テンプレートではない。部品の配置は操作の頻度、情報の依存関係、同時に見る必要性、使える幅から決める。複数候補が近い場合は、主作業を隠さず、移動や開閉の負担が少ない方を検討する。

## 早見表

| 主な作業 | 候補 | 配置を決める分岐 |
| --- | --- | --- |
| 入力・アップロードして結果を得る | P1 単一作業 | 条件を変えながら結果を見続ける必要があるか |
| 会話して調べる・考える・作る | P2 会話中心 | 根拠や成果物を会話と同時に扱うか |
| 対象を順に確認・更新する | P3 一覧・詳細 | 1件の深い確認か、多数の行の比較・一括処理か |
| 候補を絞り込んで選ぶ | P4 検索・比較 | 属性比較か、見た目の探索か。何を比較するか |
| 登録・申請を完了する | P5 フォーム・手順 | 短い記入か、論理的な段階に分かれる長い作業か |
| 状況・異常を把握する | P6 監視・分析 | どの判断からどの対応へ進むか |
| 見えている対象を直接操作する | P7 作業面・補助パネル | 操作中に結果を見る必要があるか |
| 工程・日時に対象を配置する | P8 進行・時間軸 | 主に工程間を動かすか、日時・期間を調整するか |

一覧・詳細と補助パネルの違いを意識する。前者は「選んだ対象の内容」、後者は「今の作業を助ける設定や情報」。チャット履歴は会話を選ぶ一覧、回答の引用元は会話を助ける補足であり、別の役割を持つ。[基本構造の根拠](sources.md#basic-layouts)

## P1 単一作業

**向く場面**：ファイル変換、画像解析、短い生成ツールなど、一つの入力から結果を得る流れが中心。

- PC：作業名・最小限の説明→入力と実行→状態・結果の順を基本にする。短い入力なら結果を同じページ内に置く。条件を繰り返し調整し、結果と照らし合わせるなら入力と結果を並べる。
- スマホ：入力から結果への縦の流れを保つ。実行後は結果が更新されたと分かるようにする。長い結果では入力へ戻る経路を残す。
- 低頻度の詳細条件は必要時に開く。主操作は入力との関係が分かる位置に置く。履歴が業務に必要な場合だけ履歴領域を追加する。

**避ける構成**：実行前の大きな空白、機能が一つなのに常設する全体ナビ、結果を読むために何度も開閉するダイアログ。

**別の候補へ**：会話で継続的に条件を詰めるならP2。多段の登録ならP5。画像の一部を選択しながら編集するならP7。

## P2 会話中心

**向く場面**：AI相談、社内情報の質問、会話による調査や文章作成。

- PC：会話本文を主領域にし、その下に入力部を置く。履歴を頻繁に選び直す場合は履歴一覧を隣に置ける。履歴が少なければ開く操作だけでよい。
- 引用元の確認や成果物の編集を繰り返すなら、会話と根拠・成果物を並べる。成果物の操作が中心になったら、その領域を広くして会話を補助にできる。常に会話を最大にする必要はない。
- スマホ：会話を基本にし、履歴や長い根拠・成果物は明確な操作から開く。往復時に会話位置と入力を保持する。短い引用は本文内で読めるようにする。
- 入力部は短く始め、入力に合わせて伸ばす。ソフトウェアキーボード表示中も送信と入力内容を見られる状態にする。

**避ける構成**：用途のない3列構成、根拠を見比べるたびに会話が消える構成、画面の半分を占める空の入力面、会話が不要な処理までチャットにすること。

**配置の要点**：履歴は対象の選択、引用元は補足、成果物は作業対象。これらを一つの「右サイドバー」にまとめて考えない。[補助領域の根拠](sources.md#basic-layouts)

## P3 一覧・詳細

**向く場面**：顧客・案件管理、問い合わせ対応、文書管理など、対象を選んで確認・更新する業務。

- 順次確認が中心：PCでは一覧と詳細を並べると、対象を変えながら確認しやすい。選択中の行、詳細の見出し、対象に関する操作を結び付ける。長い編集や独立した共有URLが必要なら詳細ページも候補。
- 多数の横断比較・一括処理が中心：表を主領域にする。関連する検索・絞り込みをその上、行ごとの操作を対象の行、一括操作を選択状態の近くへ置く。詳細を常設するために表を読めない幅にしない。
- スマホ：一覧→詳細の遷移を基本候補にし、戻ると検索条件・選択・位置が残るようにする。行を縦にまとめる場合も識別名、状況、次の対応を失わせない。
- 比較が必要な表は、必要な列の選択や対象を絞った比較表示を検討する。二次元の表を保つなら横スクロールを表の領域に限定し、ページ全体をはみ出させない。

**避ける構成**：業務名だけで付けるKPIカード、比較できなくなる無条件のカード化、全件詳細を縦に並べること、戻るたびに条件が消えること。

**別の候補へ**：商品を絞って比較することが主目的ならP4。工程間の移動ならP8。詳細画面内の新規登録・長い編集はP5を使える。[一覧・詳細の根拠](sources.md#basic-layouts)

## P4 検索・比較

**向く場面**：製品の選定、資料検索、設備の比較など、条件から候補を選ぶ作業。

- PC：検索条件と検索結果を近くに置く。頻繁に複数条件を変えるなら条件領域を隣へ、少数なら結果の上へ置く。検索範囲、適用中の条件、解除操作を示す。
- 見た目の探索なら画像のある一覧、仕様値の比較なら揃った行・列を優先する。比較が主目的なら、選んだ候補を同じ項目順で比べられる領域を用意する。
- スマホ：結果を主領域にし、複雑な条件は「絞り込み」から開ける。適用された条件は戻っても確認・解除できるようにする。頻繁な単純条件は画面内に残す。
- 候補の選択、詳細確認、比較への追加、確定は意味を分ける。結果ゼロでは条件を緩める行動につなぐ。

**避ける構成**：すべての条件を常に広げて結果を押し下げること、比較したい属性が各カードの別の位置にあること、選んだ候補が往復で消えること。

**配置の要点**：画像の多さだけでグリッドにしない。条件を変える頻度と比較軸から決める。画像中心の適応グリッドは基本レイアウトの一例を参考にできるが、比較表は用途に応じた追加判断。[基本構造の根拠](sources.md#basic-layouts)

## P5 フォーム・手順

**向く場面**：案件登録、申請、設定、見積条件の記入など、情報を揃えて完了する作業。

- 短いフォーム：読みやすい幅の一列を基本候補にし、関連項目をまとめる。PCで幅があるという理由だけで別の項目群を左右に分割しない。住所の一部や数値・単位など、一緒に読む短い項目は横に並べられる。
- 長いフォーム：入力項目の依存関係と利用者の理解のまとまりから段階化を検討する。項目数だけでステップ数を決めない。現在の段階、残りの見通し、戻って修正する経路を示す。
- 参照資料や見積結果を見ながら入力するなら、PCはフォームと参照・プレビューの並置を検討する。スマホは短い要約を近くに残し、長い参照を必要時に開く。
- 主操作は記入の流れの末尾へ置く。長いフォームで固定する場合は、入力欄、エラー、キーボードを隠さない。次へ、確認、確定・保存を段階に合わせて名付ける。
- エラーは対象に結び付け、長いフォームでは該当箇所に移れる要約も検討する。前後の移動やエラー後も記入済みの内容を保つ。

**避ける構成**：短い記入の過剰なウィザード化、主フォームを狭いダイアログへ押し込むこと、ステップを自由移動の全体ナビに見せること、同時に読む必要のない項目群の多列化。

**注意**：Liquid Blueの入力部品の質感を引き継ぐ。一方で、画像見本のラベル位置や列数は、このフォームの内容に合わせて変えられる。[段階化と状態保持の根拠](sources.md#forms)

## P6 監視・分析

**向く場面**：営業の状況把握、稼働監視、分析など、概況から調査・対応へ進む作業。

- 先に「何を判断し、何をするか」を定める。対応が必要な異常、重要な指標と推移、対象の詳細へ進む経路を優先順に置く。すべて同じ大きさのカードにしない。
- 期間・範囲など共通の条件は主領域の近くへまとめる。単位、比較条件、データの更新時点を分かるようにする。関連する図表だけを近くに配置する。
- スマホ：意思決定に必要な順に縦に並べる。PCの左上から機械的に積まず、対応すべき対象を埋もれさせない。複雑なグラフは要約や詳細表示を検討する。
- 指標や異常から、対象一覧・詳細や対応操作へ進めるようにする。

**避ける構成**：全PoCの初期画面をダッシュボードにすること、行動につながらないKPI、実際のデータにない傾向や警告、装飾のためのグラフ。

**別の候補へ**：対象を処理することが中心ならP3を入口にする。分析結果をレポートとして読むなら、一枚のレポートを主領域にしてよく、ダッシュボード型へ寄せる必要はない。

## P7 作業面・補助パネル

**向く場面**：AR配置、3D、地図操作、画像・文書編集など、見えている対象へ働きかける作業。

- PC：作業面に必要な広さを先に確保する。頻繁な操作は近くのツールバー、対象の選択は一覧、選択中の対象の属性は補助パネルへ分ける。対象がなければ不要な属性入力を出し続けない。
- スマホ：主対象・カメラの重要部分を残す。低頻度の選択は必要時のパネル、短い補足は下のまとまりを候補にする。主対象を見ながら調整するなら、コンパクトな非モーダル領域など、結果を隠さない配置を優先して検討する。
- 撮影、確定、取り消しなどは作業の状態に応じて配置する。ツール群が収まらなければ、頻度と関連性で整理する。小さなアイコンを隙間に詰め込まない。
- 作業面の縦横比、端末の向き、ソフトウェアキーボード、中央の認識位置・選択ハンドルを確認する。

**避ける構成**：設定を開くたびに作業結果が全面的に隠れること、固定下部メニューのために狭くなるカメラ、常設3列の強制、操作アイコンだけでの説明。

**Room AR Labからの例**：商品追加、配置調整、写真を見ることを独立した4つの行き先に見立てて固定ナビへ入れない。商品選択や短い数値入力は必要時に開ける。将来、スライダーで連続調整する要件になれば、配置結果を見ながら操作できる領域へ変える。現在のダイアログを全ツールの標準にしない。[補助パネル・操作の根拠](sources.md#basic-layouts)

## P8 進行・時間軸

**向く場面**：案件の工程管理、予約・予定、作業計画など、状態や時間の位置関係に意味がある作業。

- 工程の移動・滞留確認が中心なら、状態を列にしたボードを候補にする。日時・重複・空き枠の判断ならカレンダー、期間や依存関係なら時間軸を候補にする。
- PC：期間、担当者、対象範囲を主領域の近くに置く。詳細は選択した対象の横や別画面で扱い、ボード・時間軸を読める広さを確保する。
- スマホ：本日・選択期間の予定一覧や状態別一覧を候補にする。元の列や時刻の関係が不可欠なら、その領域内で移動できるようにし、現在の範囲や状態を見失わせない。
- ドラッグによる移動には、状態選択や日時入力などキーボード・タッチでも使える代替手段を用意する。

**避ける構成**：ステータス項目があるだけで全アプリをカンバンにすること、スマホで細い多数列を縮小すること、ドラッグのみの更新。

**別の候補へ**：多項目の精密な比較や大量更新が中心ならP3の表が適することもある。自由記入のステータス欄だけでは、移動可能な工程を推測して作らない。

## 組み合わせの判断例

| 依頼の条件 | 構成の判断例 | 判断が変わる条件 |
| --- | --- | --- |
| AIに質問して根拠をたまに確認 | P2の会話を中心にし、根拠は必要時に開く | 根拠との照合を繰り返すなら並置 |
| AIが作る提案書を直接修正 | 成果物を主領域、会話を補助にするP2＋P7 | 相談だけの段階では会話を主領域へ |
| 問い合わせを1件ずつ処理 | P3の一覧・詳細 | 一括対応と横断比較が主なら表を広く |
| 申請フォームを短時間で入力 | P5の一列フォーム | 参照資料との照合が必要なら補助領域 |
| 営業の状況を把握して対象へ対応 | P6からP3へ進む | 日常の案件処理が主ならP3を入口へ |
| ARで商品を選んで位置を調整 | P7で作業面を主領域にする | 商品の選定比較が別の大きな業務ならP4を独立 |

## PCからスマホへの判断

| 情報・操作の関係 | 狭い幅での候補 | 保つべきもの |
| --- | --- | --- |
| 一覧から対象を選ぶ | 一覧→詳細の遷移 | 条件、選択、戻る位置 |
| 主内容に短い補足が付く | 主内容の下に続ける | 主従と読む順序 |
| 低頻度の設定・選択 | 操作から開くパネル | 対象名、設定値、閉じた後の復帰 |
| 設定しながら結果を見る | 主作業が見える補助領域 | 調整と結果の対応 |
| 長い入力・編集 | 一画面の作業として開く | 入力値、保存・離脱の判断 |
| 表・地図・キャンバス | 必要な部分に限定した二次元移動 | 周囲の操作の読みやすさ |

モーダルと非モーダルは見た目で決めない。背後の作業を止めてよい短い作業か、背後を操作・確認し続ける必要があるかで選ぶ。[ダイアログの実装](sources.md#dialogs)と[狭い幅の扱い](sources.md#reflow)を確認する。
