# PoC（試作アプリ）

目的は、打ち合わせで「実際に動く」ことを見せ、動画の素材と数字を得ること。製品の品質は目指さない。手法の限界が分かることも成果になる。

## 構成

```
POCK/
├── README.md        起動・使い方・保存場所・注意して読む点・テスト・検証環境
├── start.command    ダブルクリックで起動（ブラウザも開く）
├── stop.command     ダブルクリックで停止
├── app.py など       ローカルWebアプリ
├── web/             画面（外部のCDNは使わない）
├── tests/           1コマンドで回るテスト
├── scripts/         処理の本体・計測
├── data/samples/    公開サンプル＋ sources.json（出典・取得日・使い道）
└── outputs/         結果（実行ごとのフォルダ）
```

## 作るときの約束

- **手元のMacだけで動かす**: ローカルWebアプリにし、127.0.0.1だけで待ち受け、先方のデータを外部に送らない。README にもそう書く（先方に安心してもらえる材料になる）。
  - 他のサイトからの操作（CSRF）と、localhost以外のホスト名でのアクセス（DNSリバインディング）を断る。
  - アップロードは、拡張子と中身（画像やPDFとして読めるか）を確かめ、サイズの上限を決める。
- **ポートを重ねない**: ほかの案件のPoCと同時に動かすことがある。`lsof -nP -iTCP:<ポート> -sTCP:LISTEN` で空きを確かめ、README に書く。すでに起動していれば二重に起動せず、ブラウザだけ開く。
- **ダブルクリックで起動できるように**: ユーザーがターミナルを使わずに見せられるよう、`start.command`（`.venv` がなければ案内を出す）と `stop.command` を置く。コマンドでの起動・停止も README に書く。
- **画面の型**: nas-poc-ui の型に従う。ユーザーが Google Stitch などで画面を作って承認しているなら、その画面を正とし、自分でデザインし直さない。
- **デモに使うMacで動くか**: 最初に、macOSの版・メモリ・Apple Silicon かを確かめる。新しいOS向けのツールやモデルは、古いOSで動かないことがある。重い処理（端末内のAIモデルなど）は、ほかのアプリでメモリが埋まっていると大きく遅くなる。
- **依存のライセンス**: AGPL（例: PyMuPDF）やGPLのものは、製品化のときに扱いが変わる。README の「注意して読む点」に書く。
- **公開サンプルの出典**: `data/samples/sources.json` に、出典URL・取得日・使い道を残す。
- **テスト**: 1コマンドで回るようにする。実際の処理（外部ツールを含む）も小さい入力で通し、結果は一時フォルダに書く。

## 数字を測る

動画とまとめで使う数字（処理時間・件数・精度など）は、次をそろえて記録する。

- 測った環境: 機種・メモリ・OS
- 日付
- 入力の条件: 合成音声か、公開サンプルかなど

測る前にメモリの空きを確かめ、条件を書き添える。小さいモデルと品質重視のモデルのように差が大きい場合は、両方の数字を残す。

## 動画の素材を撮る

- 公開サンプルで、実際に使う順に画面を撮る（選ぶ → 設定 → 実行中 → 結果）。
- 文字がつぶれないよう、1920×1080に収まる大きさで撮る（例: 1600×900を2倍の解像度）。
- 比較のスライダーなど、動きのある操作は、位置を少しずつ変えた連番の静止画として撮る（例: 46枚）。
- 撮影には、ブラウザを操作する道具（Playwright MCP、Chrome DevTools MCP など）を使う。Chrome DevTools MCP は利用統計を送るので、先方のURLを扱うときは `--no-usage-statistics` を付ける。
- 撮り方（サンプル・設定・解像度・ファイル名）を、動画の台本ファイルに書き残す。あとで撮り直せるように。

## README に書くこと

何の検証か／起動と停止／使い方／安全面／保存場所／結果ファイルの意味／注意して読む点（できないこと・未確認のこと）／テスト／検証環境（版）／環境を作り直すとき
