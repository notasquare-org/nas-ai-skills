# 提案用の実現性調査・PoC・紹介動画

先方の話を、打ち合わせで見せられる3つ（実現性のまとめ・動くPoC・紹介動画）にして、先方用のDriveに届けるまでの型。実際の受託案件2件で回した流れから作った。

## 流れと成果物

| # | 工程 | 成果物 | 手順の詳細 |
|---|---|---|---|
| 1 | 要件メモ | `REQUIREMENTS.md` | references/requirements-and-feasibility.md |
| 2 | 技術的に実現できるかの調査 | `research/`、`FEASIBILITY.md` | references/requirements-and-feasibility.md |
| 3 | PoC（試作アプリ） | `POCK/` | references/poc.md |
| 4 | 紹介動画（2本） | `video/out/` | references/video.md、references/voicevox.md |
| 5 | Driveへの納品 | 先方用のDriveフォルダ | references/delivery.md |

頼まれた工程だけを行う。全部か一部か分からなければ、最初に「どこまで進めますか」と1つだけ聞く。順番には理由がある。調査で「できそう」と分かってからPoCを作り、PoCで確かめた事実だけを動画で話す。

案件フォルダは `~/dev/<案件名>/` に置く。すでにあれば、その形に合わせる（動画のフォルダ名が `紹介動画/` など）。

```
~/dev/<案件名>/
├── README.md          全体の案内（何の検証か・起動方法・現在の到達点・経緯）
├── REQUIREMENTS.md    要件の正本
├── FEASIBILITY.md     打ち合わせ用の実現性まとめ
├── research/          調査の詳細と出典
├── POCK/              PoC一式
└── video/             紹介動画（台本・素材・作成スクリプト・出力）
```

## 全工程に共通する約束

### ユーザーの言葉を広げない
ユーザーが言ったことだけを「決定」と書き、AIの考えは「案」と書いて分ける。案を決定に上げるのは、ユーザーに聞いて了承を得てから。言っていない機能を足さない。以前、ユーザーが話した要望を、AIが頼まれていない機能に広げてしまい、強く否定されたことがある。足したい解釈があれば「〜という意味ですか？」と聞く。

### 質問は短く、1〜2個ずつ
音声入力で話すユーザーもいるので、長い選択肢の一覧は負担になる。固有名詞は聞き違いが起きる（PoC→「ポップ」など）。意味が二通りに取れるときは、推測で進めずに確かめる。

### 先方に見せるのは、確かめた事実だけ
数字は、PoCで実際に測ったものを、測った環境と日付つきで使う。確かめていないこと（実機での確認、実データでの精度など）は、まとめや動画の中で「未確認」「これから」と伝える。良く見せるための言い換えはしない。打ち合わせで数字の出どころを聞かれても、答えられるようにしておく。

### 先方のデータと、他社の素材
PoCは手元のMacの中だけで動かす（127.0.0.1で待ち受け、外部に送らない）。検証には公開サンプルか合成データを使い、出典を残す。他社の資料や画像を画面や動画に出すときは出典を表示し、Webなどで公開するなら差し替える。先方から受け取った資料をAIに読ませる前に、読ませてよいかをユーザーに確かめる。AIが読んだファイルの中身は、AIの提供元に送られるため。

### 価格は書かない
単価や価格はユーザーが決める。調査で分かった費用の要素（端末代、利用料など）は書いてよいが、見積もりの金額は出さない。

### 外に出す前に確かめる
Driveなど案件フォルダの外へ出すのは、ユーザーが場所を示したときだけにする。出す前に、何を・どこへ・どの名前で入れるかを示す。

### 作業場所
シェルの作業場所（cwd）を、案件のサブフォルダに置かない。GSDプラグインを使っている場合、そのフックが作業場所に `.planning/HANDOFF.json` を書き込むので、納品物のフォルダに余計なファイルが残る。パスは絶対パスで書く。

## 1. 要件メモ

`REQUIREMENTS.md` を要件の正本にし、対話のたびに更新する。書く節は「確認できたこと（決定）」「先方の話（伝聞は伝聞と書く）」「先方からの回答（日付つき）」「PoCで確かめること」「PoCで達成済みと扱わないこと」「対話で決める項目（案）」。ひな形は references/requirements-and-feasibility.md。

## 2. 技術的に実現できるかの調査

目的は、打ち合わせで「できるか」「どこまでの精度・速さなら現実的か」に答えられるようにすること。観点は、類似の製品・アプリとその精度（海外も）、使える技術とライセンス、守るべき制度・ガイドライン、費用の要素、残るリスク。出典と確認日を付け、推測は推測と書く。詳しい結果は `research/` に置き、打ち合わせ用に `FEASIBILITY.md` へまとめる（結論 → PoCで確かめたこと → 方式の候補 → 使える技術 → ルール → 残るリスクと次に確かめること）。

## 3. PoC

手元のMacで動くローカルWebアプリを `POCK/` に作る。要点は次のとおり。

- 起動と停止は、ダブルクリック（`start.command` / `stop.command`）とコマンドの両方を用意する
- ポートはほかの案件と重ねない
- 画面は nas-poc-ui の型に従う。ユーザーが Google Stitch などで作った画面があれば、それを正とする
- 数字を測り、環境と日付を残す
- デモに使うMacで動くかを先に確かめる
- 動画用の画面を、公開サンプルで使う順に撮る

詳細は references/poc.md。

## 4. 紹介動画

### 型（どの案件でもこの順）

| # | 場面 | 中身 |
|---|---|---|
| 1 | タイトル | 「〈先方名〉様向け 検証版（PoC）のご紹介」、価値をひとことで、アプリ名、株式会社Not a Square・年月 |
| 2 | いまの課題 | 先方の今の作業を3段階ほどで見せ、困りごとを示す。最後に「この〜を短くすることが目的です」 |
| 3 | 解決のしかた | PoCの画面を、使う順に1場面1つずつ。動画の中心で、全体の半分ほど |
| 4 | 到達点 | 確かめたこと（✓）と、まだのこと（△）。数字は測ったものだけ |
| 5 | 次の一歩 | 先方に頼みたいこと（例:「御社の実際のデータで、試させてください」） |
| 6 | 終わり | 「ご覧いただき、ありがとうございました」と、クレジット |

全体で1.5〜2分、1920×1080・30fps。文の書き方は references/video.md。

### 2本作る
- **声・BGM付き**: 先方に送って見てもらう用。ナレーション、BGM、字幕（または画面の文字）、最後にクレジット「ナレーション：VOICEVOX:冥鳴ひまり ｜ BGM：オリジナル（Not a Square 制作）」を入れる。
- **音なし**: 打ち合わせで、ユーザーが話しながら流す用。画面の文字だけで流れが分かるようにする。

### 声とBGMの権利
声は VOICEVOX の冥鳴ひまり（スタイルID 14、速さ1.05）を既定にする。商用・法人の利用ができ、申請は要らない。クレジットの表記は必要。macOSの読み上げ音声（say、Kyoko など）は使わない。Appleの規約で個人的・非商用の利用に限られ、提案動画には使えない。ほかの声は、エンジンから利用規約を読んでから使う（references/voicevox.md）。BGMは `scripts/bgm.py` で合成したオリジナルを使う。

### 作り方を選ぶ（案件ごと）
- **A. HTMLアニメ方式**（`scripts/html-video/`）: 流れや考え方を、動きで見せたいとき。場面をHTMLで作り、Chromeで1コマずつ描く。声が場面より長いときは、表示し終えた所で止めて待つ。
- **B. スライド＋字幕方式**（`scripts/slide-video/`）: PoCの実際の画面を、操作の順に見せたいとき。画面写真を撮り直せば作り直せる。

迷ったら、理由を1行添えて案を出し、ユーザーに選んでもらう。どちらも場面の型は同じ。手順は references/video.md。VOICEVOX の準備は `python3 scripts/voicevox.py status` から始める。

### 書き出したら確かめる
長さ、音（声・BGM付きの版の音量がおよそ −16 LUFS で、音なし版に音声がないこと）、各場面の静止画（文字のはみ出し・誤字・出典・クレジット）、数字が `FEASIBILITY.md` と合っているかを確かめる。静止画は自分で開いて見る。

## 5. Driveへの納品

ユーザーが示した先方用のフォルダに、「見せるものだけ」（基本は動画2本）を入れる。コードや作業用の文書は入れない。手順は次のとおり。

1. 1ファイル10MBを超えるものは `scripts/shrink_for_drive.sh` で縮める
2. 入れる前にフォルダの中身を見て、二重に入れない
3. 作り直した版は差し替える。古い版をゴミ箱に入れるかは、ユーザーに聞いてから

詳細は references/delivery.md。

## 終わりの報告

作ったもの（パスとDriveのリンク）、確かめたこと、確かめていないこと、ユーザーが決めること（価格、見せる範囲など）を、短く報告する。

## このスキルを育てる

新しい案件で、ここに書いていない落とし穴に当たったら、該当する references/ のファイルに「何が起きたか・どうするか」を1〜2行で足す。案件名や先方の情報は書かない。
